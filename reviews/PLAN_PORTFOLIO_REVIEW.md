# 포트폴리오 계획 리뷰 결과

> 보존 상태: 이 리뷰는 토스페이먼츠 계약 중심 재설계 전 기준선입니다. 아래 프로젝트명과 판정은 현재 계획에 자동 승계되지 않습니다.

## 종합 판정: REJECT

경력 수준 기준: **1~3년차 Java/Spring 금융 백엔드**

판정 이유: 현재 저장소에는 구현, 테스트 결과, 배포, 측정치가 없고 계획만 존재합니다. 계획의 시장 정렬도와 문제 구성은 유효하지만, 계획을 성과로 승격할 수 없으므로 현재 포트폴리오는 REJECT입니다.

이 판정은 기획을 폐기하라는 뜻이 아닙니다. 각 프로젝트가 실제 evidence를 확보한 뒤 개별 PASS로 전환돼야 한다는 기준선입니다.

## 입력과 커버리지

- 대상: `README.md`, `MASTER_PLAN.md`, `docs/`, 12개 프로젝트 계획과 종료 기준
- 이미지: 계획 단계에는 대시보드·아키텍처 실측 이미지 없음
- 채용 기준: [MARKET_ALIGNMENT.md](../docs/MARKET_ALIGNMENT.md)의 공식 공고 표본
- 수치: 일정·회차 외 성과 수치 없음
- 구현 상태: 전 프로젝트 PLANNED

## 정합성 감사

| 항목          | 위치               | 심각도    | 주장과 근거                                          |
| ------------- | ------------------ | --------- | ---------------------------------------------------- |
| 기술 스택     | `TECH_BASELINE.md` | 해당 없음 | 계획 스택이며 사용 경험으로 주장하지 않음 — `[가정]` |
| 2주 일정      | `MASTER_PLAN.md`   | 해당 없음 | 캘린더 계획이며 성과가 아님 — `[가정]`               |
| 성능·AI 품질  | 전체               | 해당 없음 | 측정치가 없어 평가 불가 — `[불명]`                   |
| 클라우드 운영 | 06·최종 감사       | 해당 없음 | 임시 배포 계획이며 운영 경험 아님 — `[가정]`         |

서로 대조할 실제 숫자와 이미지가 없으므로 정합성 결함이 없다고 판정하지 않습니다. 현재는 **감사 대상 근거 없음**입니다.

## 영역별 평가

| 영역            | 현재 등급   | 근거                                                                                                  |
| --------------- | ----------- | ----------------------------------------------------------------------------------------------------- |
| 기술적 의사결정 | 적합 가능성 | 모듈러 모놀리스 우선, 결제 경계만 분리 실험, AI 권한 제한 등 선택 원칙이 있으나 실제 대안 비교가 없음 |
| 문제 해결 과정  | 적합 가능성 | 금융 불변식과 실패 시나리오가 계획돼 있으나 실패·수정 과정이 아직 없음                                |
| 성과·임팩트     | 부적합      | 재현 가능한 측정, 배포, 사용자 또는 기술 결과가 없음                                                  |

세 영역이 모두 적합 이상이 아니므로 REJECT입니다.

## 포트폴리오 구성 평가

- 기술적 범위: 금융 정합성, 결제 신뢰성, AI 통제를 일관된 플랫폼 안에 연결해 범위는 적절합니다.
- 난이도 분포: 초반의 결정론적 금융 코어에서 후반의 분산 장애와 비결정론적 AI로 난도가 증가합니다.
- 포지션 정렬도: 공식 공고 표본의 트랜잭션·배치·장애·보안·AI 운영 항목과 높은 관련성이 있습니다.
- 스토리텔링: 네 대표 사례와 12개 진화 타임라인 분리는 합리적입니다.
- 과장 감사: 계획 문구 자체는 제한을 명시했지만, 구현 후 결과 요약에서 다시 검증해야 합니다.

## 강점

- 금융 핵심 로직과 AI를 분리하고 AI를 보조·제안 역할로 제한했습니다.
- 모듈러 모놀리스에서 시작해 서비스 분리가 실제로 이득인지 검증하도록 했습니다.
- 프로젝트 종료 조건에 정합성·원본 evidence·레드팀을 포함했습니다.
- 실제 사용자와 규제 인증이 없는 개인 프로젝트의 한계를 선제적으로 밝혔습니다.

## 개선이 필요한 지점

- 모든 기술 선택은 아직 계획자가 정한 가설입니다. 실제 구현 과정에서 선택이 바뀌면 바뀐 이유를 ADR에 남겨야 합니다.
- 2주 범위가 여전히 넓은 프로젝트가 있습니다. 필수 범위가 밀리면 확장 범위를 제거해야 합니다.
- 성능 개선을 목표로 먼저 쓰지 말고 기준선 측정 뒤 실험 질문을 확정해야 합니다.
- FDS와 RAG는 데이터·평가 설계가 결과보다 중요하므로 test set 오염을 막아야 합니다.
- 임시 AWS 배포는 실제 운영과 협업 경험을 대체하지 못합니다.

## 재평가 규칙

각 프로젝트 종료 시 해당 폴더를 독립 입력으로 다시 평가합니다. `적합 가능성`이라는 표현은 실제 PASS로 이어지지 않으며, 증거 없는 항목은 그대로 부적합 또는 불명으로 둡니다.
