# 프로젝트 01 도메인 브리프 — 결제 사실을 설명하는 원장

## 상태

- 문서 상태: `[가정]`
- 적용 프로젝트: `01-ledger-core`
- 외부 문서 확인일: 2026-08-28
- 제품 기준: [토스페이먼츠 공개 계약 기반 PG 샌드박스](../../docs/PRODUCT_VISION.md)

이 문서는 구현 전에 도메인 예제와 검증 질문을 고정합니다. 아직 journal·posting 기능을 완료했다는 증거가 아닙니다.

## 해결할 사용자 문제

상점 운영자는 합성 PG가 `10,000원 결제 완료`를 반환했다는 결과뿐 아니라 다음 질문에 답할 수 있어야 합니다.

- 어느 주문과 외부 결제 식별자에서 생긴 금액인가?
- 내부에서 상점에 지급해야 할 금액은 어떤 기록으로 설명되는가?
- 같은 결과가 두 번 들어와 금액이 중복되지 않았는가?
- 결제가 취소됐을 때 원본을 지우지 않고 어떤 반대 기록을 남겼는가?

프로젝트 01은 샌드박스 세션 생성과 승인·조회 선택 계약을 구현합니다. 승인 사실을 불변 journal과 posting으로 기록하되, 취소·웹훅·가상계좌·정산은 뒤 프로젝트로 미룹니다.

## 공식 문서에서 관찰한 행위

토스페이먼츠 공개 문서에서 확인한 외부 행위는 다음과 같습니다.

1. 결제는 요청, 인증, 승인 단계로 진행되며 상점 서버가 승인 전에 `orderId`와 금액을 대조합니다.
2. `paymentKey`는 결제 승인·취소·조회에 사용하는 결제 식별자입니다.
3. 승인된 결제는 `DONE`, 전체 취소는 `CANCELED`, 부분 취소는 `PARTIAL_CANCELED`로 표현될 수 있습니다.
4. POST 요청은 `Idempotency-Key`를 사용할 수 있습니다.

## 프로젝트가 내린 결정

다음은 토스페이먼츠의 내부 설계가 아니라 프로젝트 01의 학습용 결정입니다.

- 합성 `paymentKey`를 journal의 외부 참조에 연결합니다.
- 원장의 source of truth는 확정된 journal과 두 개 이상의 posting입니다.
- 같은 `paymentKey`로 승인을 다시 제출해도 새 Payment·journal을 만들지 않습니다. 이 aggregate 중복 방어는 공개 `Idempotency-Key` 응답 재생 계약이 아닙니다.
- 같은 `paymentKey`를 다른 orderId·amount에 재사용하면 충돌입니다.
- 확정 journal과 posting은 수정·삭제하지 않습니다.
- 취소와 정정은 새 journal의 반대 posting으로 표현합니다.
- 프로젝트 01은 승인에 필요한 최소 Payment 상태만 저장합니다. 취소와 전체 상태 전이는 프로젝트 02에서, 내부 엔진의 호환 이전은 프로젝트 07에서 다룹니다.

## 액터와 책임

| 액터 | 프로젝트 01에서의 책임 |
| --- | --- |
| 샘플 상점 | 주문과 금액을 정하고 샌드박스 세션을 생성한 뒤 승인 요청 |
| 합성 PG | 세션의 paymentKey/orderId/amount 검증과 Payment 응답 생성; 실제 결제망 호출 없음 |
| 원장 모듈 | 승인 사실의 균형·통화·불변성·중복 외부 참조 검증 |
| 운영자 | journal과 account posting을 조회; 원본 수정 권한 없음 |

## 용어와 식별자

| 용어 | 의미 | 프로젝트 01 표현 |
| --- | --- | --- |
| `orderId` | 상점이 만든 주문 식별자 | MID 안에서 유일한 Payment 조회 키 |
| `paymentKey` | 결제 식별자 | 샌드박스 세션이 만든 Payment·journal 연결 키 |
| journal entry | 하나의 금전 사실을 설명하는 기록 | 두 개 이상의 posting을 원자적으로 포함 |
| posting | 특정 account의 차변 또는 대변 변화 | 양수 금액과 하나의 통화를 가짐 |
| reversal | 기존 사실을 지우지 않는 반대 기록 | 원본 journal을 참조하는 새 journal |

`orderId`와 `paymentKey`의 실제 형식이나 수명은 모방하지 않습니다. 테스트에서는 실제 고객·가맹점 데이터가 아닌 명시적인 합성 ID를 사용합니다.

## 금액 흐름과 원장 예제

아래 계정과 분개는 원장 불변식을 학습하기 위한 `[가정]`입니다. 실제 토스페이먼츠의 계정과목이나 회계처리를 나타내지 않습니다.

### 합성 결제 확정 10,000 KRW

| account | 유형 | debit | credit |
| --- | --- | ---: | ---: |
| `PG_CLEARING_RECEIVABLE` | 자산 | 10,000 | 0 |
| `MERCHANT_SETTLEMENT_PAYABLE` | 부채 | 0 | 10,000 |
| 합계 |  | 10,000 | 10,000 |

이 예제는 외부에서 받을 금액과 상점에 지급할 의무를 같은 journal에 기록한다는 합성 학습 모델입니다. 실제 승인·매입·입금 시점은 비범위이며, 프로젝트 08은 합성 transaction과 정산 확정 시점만 별도 모델링합니다.

### 전체 취소 10,000 KRW

| account | 유형 | debit | credit |
| --- | --- | ---: | ---: |
| `MERCHANT_SETTLEMENT_PAYABLE` | 부채 | 10,000 | 0 |
| `PG_CLEARING_RECEIVABLE` | 자산 | 0 | 10,000 |
| 합계 |  | 10,000 | 10,000 |

취소 journal은 원본 journal을 삭제하거나 금액을 0으로 수정하지 않습니다. 새 외부 참조와 원본 journal 참조를 가진 반대 기록으로 남깁니다.

## 불변식과 테스트 연결

| 불변식 | 대표 테스트 |
| --- | --- |
| 한 journal의 debit·credit 합계가 통화별로 같다 | 10,000/10,000 성공, 10,000/9,999 거절 |
| posting 금액은 0보다 크다 | 0·음수 거절 |
| 한 journal에서 서로 다른 통화를 상계하지 않는다 | KRW debit과 USD credit 거절 |
| 저장은 journal과 모든 posting에 원자적이다 | 두 번째 posting 실패 뒤 row가 남지 않음 |
| 같은 paymentKey는 중복 금액을 만들지 않는다 | 같은 승인 재제출과 다른 orderId·amount 재사용 충돌; 공개 멱등 응답 재생은 제외 |
| 확정 기록은 수정·삭제하지 않는다 | repository와 DB 최종 방어 우회 시도 |
| 정정 뒤에도 시점별 잔액을 재계산할 수 있다 | 원본 직후와 reversal 직후 잔액 비교 |

## 실패·재시도·복구 표

| 상황 | 기대 결과 | 다음 프로젝트 연결 |
| --- | --- | --- |
| 같은 합성 `paymentKey`와 같은 승인 재제출 | 새 Payment·journal 없이 기존 확정 상태로 수렴; 공개 응답 재생 계약은 아님 | 02 공개 멱등 요청 경쟁 |
| 같은 합성 `paymentKey`와 다른 금액 | 충돌, 새 journal 없음 | 02 결제 command |
| posting 저장 중 DB 오류 | 전체 rollback | 03 outbox transaction |
| 확정 journal update·delete | 거절과 감사 가능한 오류 | 05 권한·감사 |
| 승인 응답 유실 | paymentKey 또는 orderId 조회로 결과 확인 | 02 멱등 재시도 |
| 취소 요청 | 프로젝트 01에서는 거절 또는 미노출 | 02 부분·전체 취소 |

## 미확인과 비범위

- 토스페이먼츠가 내부적으로 복식부기 원장을 사용하는지와 그 schema는 `[불명]`입니다.
- 실제 승인, 매입, 카드사 입금과 상점 정산 사이의 회계 인식 시점은 이 예제로 확정하지 않습니다.
- 실제 PG 수수료, 부가세, 에스크로, 정산 주기와 영업일 계산은 구현하지 않습니다.
- `paymentKey`를 실제 토스페이먼츠 API에서 받거나 실거래에 사용하지 않습니다.
- 프로젝트 01의 원장 예제는 회계·세무 자문이나 실제 재무제표 모델이 아닙니다.

## 설명할 수 있어야 하는 질문

1. 외부 결제 식별자와 내부 journal ID를 왜 분리했나요?
2. 결제 취소 때 원본 journal을 수정하지 않는 이유는 무엇인가요?
3. 승인 사실과 실제 정산 완료가 다를 수 있는데 왜 프로젝트 01에서는 하나의 합성 사실로 제한했나요?
4. 같은 외부 참조의 재시도와 잘못된 재사용을 어떻게 구분하나요?
5. 이 원장 모델에 대해 토스페이먼츠의 내부 구현이라고 주장할 수 없는 이유는 무엇인가요?
